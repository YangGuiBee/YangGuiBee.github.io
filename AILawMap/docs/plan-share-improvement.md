## 0. 목적

지금까지 AILawMap은 "내가 만든 결과물을 보여주는 사이트"였다. 목표는 여기서 한 걸음 나아가
**남(학생·연구자 등)이 찾아서 쓰고, 필요하면 남이 보태기도 하는 공개 리소스**로 만드는 것.
RestroomMap·KIS 등 다른 프로젝트도 같은 방향을 염두에 두고 있지만, 87개 법령 페이지로 콘텐츠가
가장 두터운 AILawMap을 첫 착수 대상으로 정했다.

이 문서는 **구현 계획이 아니라 확인용 초안**이다. 4장의 Phase안은 귀비님 확인 후 범위를 좁혀서
착수한다.

## 1. 참고 사례에서 가져올 핵심 요소

### 1-1. PAX (hollobit.github.io/PAX)

"보여주는 사이트"와 "찾고 보태는 사이트"의 차이는 아래 세 가지로 요약된다.

| 요소 | PAX의 구현 |
|---|---|
| 딥링크 검색 | 검색어가 URL 쿼리에 남음(`?q=김창일`) → 결과 하나를 링크로 공유 가능 |
| 필터·태그 | 기관유형/출처 등으로 좁혀보기, 북마크 |
| 기여 경로 | Threads/오픈채팅 → GitHub로 이어지는 크라우드소싱 파이프라인 |

### 1-2. 경기도의회 지능형 법령정보시스템 (ggc-lexdiff.vercel.app)

법령 도메인 자체가 같은 사이트라 더 직접적으로 참고할 만한 사례. 공직자 대상으로 "법률 용어 대신
일상 언어"로 법령을 찾게 하는 것이 목적이며, 법제처 API를 실시간 연동하는 대시보드형 서비스다.
AILawMap과 겹치는 지점과 다른 지점을 구분해서 봐야 한다.

| 요소 | ggc-lexdiff의 구현 | AILawMap과의 관계 |
|---|---|---|
| 위임법령 3단 비교 | 법률·시행령·시행규칙을 계층적으로 나란히 비교 | AILawMap의 "법+시행령 토글"과 **같은 문제의식**. 다만 토글(숨김/보임)이 아니라 나란히 놓고 비교하는 UI라는 점이 다름 → Phase 4 후보로 아래 반영 |
| 신구법 대조표 | 법 개정 전/후 조문을 대조 | AILawMap은 개정 이력을 추적하지 않는 정적 스냅샷 구조라 지금 범위 밖. 다만 법이 개정될 때마다 페이지를 갱신만 하고 있어, 향후 "몇 차례나 개정됐는지"를 남기는 정도는 저비용으로 고려 가능 |
| 변경 영향 분석 (상위법 개정→하위법 영향 자동탐지) | 법제처 API로 실시간 자동탐지 | AILawMap이 이미 수작업으로 하고 있는 것(AI기본법 조문↔개별법 연결, `ai-note`)의 **자동화 버전**. 지금은 사람이 조문을 읽고 연결을 설계하는 방식이라 자동탐지로 대체하기엔 이름 |
| AI 법률분석(자연어 질의) | LLM 기반 질의응답 | 서버리스 함수 1개 + 무료 LLM(큐엔 등)으로 비용 리스크 없이 가능하나, 법령 정보라 할루시네이션 위험 관리가 필요 → Phase 4에 **조건부 후보**로 반영(확정 아님) |
| 실시간 법제처 API 연동 | 항상 최신 조문 | 완전한 실시간 대신, GitHub Actions 주간(일요일) 갱신 + PR 확인으로 "근실시간" 절충 → Phase 4에 **확정** 반영 |

## 2. AILawMap 현재 상태 진단

`C:\AI\AILawMap` 구조를 직접 확인한 결과:

- **콘텐츠**: `laws/` 아래 법령 페이지 87개(국내법 + 국제규범 14개 포함), `index.html` 하나의
  SVG 다이어그램에서 전체를 클릭 탐색하는 구조.
- **검색은 이미 있음, 그러나 제한적**: `index.html`에 `#lawSearchInput` 검색창이 있고
  `runSearch()`가 SVG 다이어그램의 `a.node-link` 요소들의 `<title>` 텍스트(법령명 + 한 줄 설명)를
  대상으로 하이라이트한다. 즉:
  - 검색 대상이 **다이어그램 노드 타이틀뿐** — 각 법령 페이지 본문(조문 설명, 절차구조도 텍스트)은
    검색되지 않는다.
  - 검색어가 URL에 반영되지 않아 **결과를 링크로 공유할 수 없다**.
- **필터·태그: 없음.** 다이어그램의 열(x좌표) 배치가 "국내법 계열/국제규범" 같은 암묵적 분류
  역할을 하고 있지만, 명시적으로 필터링하거나 태그로 좁혀보는 UI는 없다.
- **기여 경로: 없음.** 오탈자·누락 법령을 제보할 채널이 없다.
- **기술 스택**: 프레임워크 없이 순수 HTML/CSS/JS, 빌드 도구 없음(정적 GitHub Pages).
  법령 페이지는 Python 스크립트(`build_pages.py` 계열)로 생성. 이 구조는 유지하는 게
  KISS/YAGNI에 맞다 — 검색 기능도 별도 서버 없이 클라이언트 JS로 해결 가능하다.

| 항목 | PAX | AILawMap 현재 | 격차 |

## 4. 개선 방향

> **범위 확정 (2026-08-23)**: Phase 1은 지금 개발 착수, Phase 2는 운영하면서 필요성이
> 보이면 추가 검토(지금 계획·개발 대상 아님), Phase 3는 GitHub Issue 대신 이메일 제보로
> 대체 확정. 아래 각 Phase 설명에 반영.

### Phase 1: 전체 검색 + 딥링크 (확정 — 지금 개발 착수)

- **목표**: 법령명뿐 아니라 조문 설명까지 검색되게 하고, `index.html?q=키워드` 형태로 접속하면
  자동으로 그 검색이 실행되게 한다.
- **인덱스 깊이 (확정, 2026-08-23) — 조문 설명까지 포함**: 법령명 수준만 넣는 얕은 인덱스가
  아니라, 87개 법령 페이지 각각의 "[2] 절차 구조도" 안 `wf-node` 텍스트(조문번호 `pcode` +
  설명 `t`, 예: "제24조제2항 — 누적연산량 산정방식 고시")까지 전부 인덱싱한다. 작업량은
  더 들지만, **법 이름을 몰라도 개념·키워드로 검색이 가능**해야 한다는 게 결정 이유.
  - 검색 결과는 법령 페이지 전체가 아니라 **해당 조문 노드까지 바로 이동**하는 딥링크
    (`ai-basic-act.html#P13` 같은 앵커)로 연결한다.
- **국제규범(14개) 포함 여부 (확정, 2026-08-23) — 포함**: 국내법과 동일하게 검색 대상에
  넣는다. 직접 확인한 결과(EU AI Act·NIST AI RMF·OECD AI원칙·ISO 42001·seoul-declaration·
  un-ai-resolution·china-generative-ai-measures 등) 14개 전부 국내법과 **동일한
  `wf-node`/`pcode`/`t` 구조**를 쓰고, 설명 텍스트(`t`)도 전부 한국어라서 별도 파서 없이
  하나의 스크립트로 87개 전부 처리 가능 — 추가 비용이 거의 없다.
  - **파서 설계 시 주의점 하나**: "[2]" 섹션 제목이 법령 유형마다 다르다(국내법·EU AI Act는
    "절차 구조도", NIST는 "기능 구조도", OECD·UNESCO는 "원칙 구조도", ISO는
    "관리체계 구조도"). 섹션 제목 문자열로 필터링하면 NIST·OECD·ISO 같은 페이지를 놓치므로,
    **섹션 제목과 무관하게 페이지 전체의 `.wf-node`를 스캔**하도록 만든다.
  - 조문 인용 라벨(`제24조제2항`/`Article 3`/`원칙 1.1`/`절 5`/`MEASURE 3`)과 원문 링크
    출처(law.go.kr 외에 EU/OECD/ISO/NIST 등 각기 다른 사이트)는 형식을 통일하지 않고
    그대로 노출한다 — 검색 기능에는 영향 없음.
- **구현 후보**:
  1. **(권장) 빌드타임 인덱스**: `build_pages.py`와 같은 계열의 **새 Python 스크립트**를 만들어
     `laws/*.html` 87개를 순회하며 각 `wf-node`의 `id`(앵커)·`pcode`(조문번호)·`t`(설명 텍스트)와
     법령명·페이지 경로를 뽑아 검색용 JSON으로 저장 → `index.html`은 이 JSON을 fetch해서
     클라이언트에서 단순 문자열 매칭. 87개 페이지를 런타임에 매번 fetch하는 방식보다 훨씬 가볍다.
  2. 런타임 fetch 방식은 비권장(페이지 수가 늘수록 느려짐, KISS에도 안 맞음).
- **딥링크**: `index.html` 로드 시 `URLSearchParams`로 `q` 파라미터를 읽어 검색창에 채우고
  `runSearch()`를 자동 실행. 검색 실행 시 `history.replaceState`로 현재 검색어를 URL에 반영.

### Phase 2: 필터·태그 (보류 — 운영하면서 추가 검토)

- 지금 계획·개발 대상에 넣지 않는다. Phase 1을 실제로 운영해보고 나서, 정말 필요하다고
  판단되면 그때 다시 설계한다(YAGNI — Phase 1 사용 경험 없이 미리 설계하면 틀릴 위험이 큼).
- 후보 축은 참고용으로만 남겨둠: 국내법/국제규범 구분, AI기본법 직접연결 조문 유무
  (`ai-note` 클래스가 이미 있는 법령들), 소관부처 등. 다이어그램의 열 구조를 그대로 태그로
  승격하는 방식이 가장 적은 추가 작업으로 가능해 보인다는 정도만 기록.

### Phase 3: 기여 경로 (확정 — 이메일 제보)

- GitHub Issue 템플릿 대신 **이메일 제보**로 확정. `index.html`(및 필요하면 각 법령 페이지)
  한구석에 "오류·누락 법령 제보: guibee1004@gmail.com" 한 줄만 표시한다.
- **GitHub Issue를 쓰지 않기로 한 이유**: AILawMap을 보는 사람(학생·연구자·법률 실무자)이
  GitHub 계정을 갖고 있지 않을 가능성이 높아, Issue 방식은 진입장벽이 있다고 판단(귀비님과
  논의 중 확인). 이메일은 누구나 바로 쓸 수 있어 훨씬 가볍다.
- 별도 백엔드(Apps Script, Google Form 등)도 필요 없다 — 정적 HTML에 `mailto:` 링크
  하나만 추가하면 끝나는 가장 KISS한 방식.

### Phase 4 (장기, 검토용 — ggc-lexdiff에서 착안)

Phase 1~3보다 후순위. 지금 바로 계획에 넣자는 게 아니라, 나중에 콘텐츠가 안정된 후 검토할
후보로만 남겨둔다.

- **법+시행령 비교 페이지 (확정 — 인공지능기본법 쌍만)**: 현재 "시행령 토글"(버튼 눌러야
  시행령 노드가 보이는 방식) 대신, ggc-lexdiff의 "위임법령 비교"처럼 법률·시행령을 처음부터
  나란히 놓고 보는 별도 비교 페이지를 **인공지능기본법 ↔ 인공지능기본법 시행령 한 쌍에만**
  추가한다. 다른 86개 법령에는 적용하지 않음(YAGNI — 전면 재작업 비용을 피하고, 이 프로젝트의
  중심 법령인 인공지능기본법에만 힘을 싣는다).
  - 법제처 DRF 검색 API로 확인한 결과, 인공지능기본법은 **법률-시행령 2단 구조**이고
    시행규칙(부령)은 존재하지 않는다(2026-08-23 확인, `법령ID 014820`/`015032`). 따라서
    "3단 비교"가 아니라 **2단 비교 페이지**가 된다.
  - 87개 페이지에 이미 적용된 토글 방식([[feedback_lawmap_common_ui_rules]])은 그대로 두고,
    이 비교 페이지는 별도 페이지(예: `laws/ai-basic-act-compare.html`)로 신설하는 쪽이
    기존 구조를 건드리지 않아 안전하다.
- **개정 감지 + 데이터 갱신 (확정 — GitHub Actions, 매주 일요일)**: 지금은 87개 법령이
  개정됐는지 아무도 자동으로 알 수 없고, 사람이 우연히 law.go.kr을 다시 봐야만 알아채는
  구조([[reference_lawgokr_drf_api]]). 이를 GitHub Actions cron으로 경량 자동화한다.
  ("실시간 API 연동"에 대한 절충안이기도 하다 — 완전한 실시간은 아니지만 최대 1주 지연의
  근실시간을 서버 없이 확보한다.)
  - **주기**: 매주 일요일 워크플로 실행.
  - **수집**: 87개 법령의 `MST`(법령ID)로 DRF 검색 API(`lawSearch.do`)를 호출해 최신
    `공포일자`/`시행일자`를 가져온다.
  - **반영 방식(직접 push 아님)**: main 브랜치에 바로 커밋·push하지 않는다. Actions가
    별도 브랜치에서 스냅샷 JSON(`docs/law-snapshot.json`)을 갱신한 뒤 **Pull Request를
    자동 생성**한다. PR 설명에 이전/신규 공포일자·시행일자가 달라진 법령 목록과 law.go.kr
    링크를 적어둔다. **PR을 확인하고 merge(=push 확정)하는 건 귀비님이 직접 한다** — 이게
    "push 확인은 사람이 한다"는 원칙을 지키는 지점이다.
  - **페이지 본문은 자동으로 다시 쓰지 않음**: 구성/절차구조도를 조문 읽고 재설계하는 건
    사람 영역이라, 이 워크플로는 "스냅샷 데이터 갱신 + 변경 알림"까지만 하고, 실제 법령
    페이지 콘텐츠 반영은 기존 수동 파이프라인(curl DRF → Python 스크립트 → Node.js 검증 →
    배포)을 그대로 따른다.
- **개정 이력 최소 기록 (확정)**: 신구법 대조표까지는 아니어도, 법령 페이지에 "최근 개정일/
  개정 횟수"만 표시하는 저비용 버전.
  - **저장**: 위 개정 감지용 스냅샷 JSON(`docs/law-snapshot.json`)을 "덮어쓰기"가 아니라
    "누적 배열"로 바꾸면 그 자체가 개정 이력이 된다(새 파일 불필요).
  - **표시**: 법령 페이지 하단 "기준일" 문구 옆에 한 줄만 추가한다. 예:
    `개정 이력: 2025-01-21 제정 · 2026-01-20 일부개정 · 2026-08-18 시행령 개정 (총 3회)`.
    이 한 줄을 클릭하면(또는 옆에 작은 링크로) **law.go.kr 자체 연혁 페이지로 나가는 링크만**
    단다 — 조문 대조 화면을 우리가 직접 만들지 않는다.
  - **하지 않는 것**: 과거 조문 전문 보관, 조문 단위 신구 대조(diff) 화면 — 둘 다 데이터량·
    유지비용이 커서 YAGNI(1-2절 "신구법 대조표"와 동일 사유로 제외).
- **AI 자연어 질의 (조건부 후보 — 무료 LLM 연동, 확정 아님)**: "서버가 전혀 필요없는 방법"은
  없지만, 무료 LLM을 쓰면 최소한 **비용 리스크는 없앨 수 있다**.
  - **왜 서버(정확히는 서버리스 함수 1개)는 여전히 필요한가**: LLM API 키를 브라우저 JS에
    그대로 두면 누구나 훔쳐 쓸 수 있어 안 된다. `contact.js`가 Google Apps Script를 백엔드로
    쓰는 것과 같은 패턴으로, 서버리스 함수(Apps Script 또는 Cloudflare Worker 등) 하나가
    키를 숨기고 LLM API를 대신 호출해줘야 한다. 이 구조 자체는 이미 이 생태계에 있는
    패턴이라 새로 배울 건 없다.
  - **무료 LLM으로 비용 리스크 제거**: 큐엔(Qwen) 등 무료 API 티어를 제공하는 모델(또는
    Gemini/Groq 무료 티어 등)을 쓰면 사용량이 몰려도 과금이 아니라 **요청 제한(rate limit)에
    걸려 일시적으로 안 되는 정도**로 실패 방식이 안전해진다. 유료 API의 "무한 과금" 리스크와는
    질적으로 다르다.
  - **범위를 반드시 좁혀야 하는 이유(법령 정보이기 때문)**: LLM이 조문을 자유롭게 생성해서
    답하게 하면 없는 조문을 지어내는(할루시네이션) 위험이 있다 — 법령 정보 사이트에서는
    치명적이다. 따라서 "LLM이 법을 직접 답한다"가 아니라, **"LLM은 사용자의 일상어 질문을
    검색어로 바꿔서 Phase 1 검색 인덱스를 찾아주는 역할만 한다"**(RAG 중 검색 단계 보조 역할)로
    한정하는 게 안전하다. 최종 답은 항상 우리 법령 페이지로 연결하고, 텍스트를 새로 생성해서
    보여주지 않는다.
  - **남은 리스크**: 무료 티어 정책은 제공사가 언제든 바꾸거나 없앨 수 있다 → LLM 호출부를
    독립된 작은 모듈로 분리해두면 나중에 제공사를 바꾸는 비용을 낮출 수 있다.
  - 이 항목은 Phase 1~3과 별개로, **하고 싶어질 때 별도로 다시 논의**하는 것을 권한다(지금
    계획의 실행 대상에는 포함하지 않음).
- **실시간 법제처 API 연동**: 위 "개정 감지 + 데이터 갱신" 항목으로 절충안이 확정됐으므로
  별도 항목에서는 제외.
